## C/C++ 소스 분석 (clangd + gtags 2트랙)

C/C++ 코드 탐색은 성격이 다른 두 도구를 역할 분담해 사용한다.

| 상황 | 도구 | 키 |
|------|------|----|
| 정의 점프, 자동완성, 진단, 이름 변경 | **clangd** (의미 기반, 정밀) | `Ctrl-]`, `gd`, `K` |
| 전체 트리 심볼/참조/호출자 검색 | **gtags** (색인 기반, 대형 트리에 강함) | `Ctrl-\` + 문자 |

### 정의 점프 (Ctrl-])

`Ctrl-]` 하나로 사용 가능한 백엔드를 자동 선택한다.

- clangd가 연결되어 있으면 clangd 정의를 우선 사용
- clangd가 없거나 정의를 못 찾으면 gtags로 자동 폴백
- 둘 다 없으면 안내 메시지만 출력 (에러 없음)
- `Ctrl-t` 로 점프 전 위치로 복귀 (태그 스택)

### clangd용 compile_commands.json 생성 (ccgen)

clangd가 헤더를 못 찾거나, 열어본 적 없는 `.c`의 구현부로 점프가 안 될 때 사용한다.

```
:CCGen              " 전체 트리: 스캔 → include 추론 → compile_commands.json 생성 → clangd 재시작
:CCGen src lib      " 지정 디렉토리만 (루트 기준 상대 경로, 복수 가능)
:CCGen .            " 현재 작업 디렉토리만
:CCGen %            " 현재 편집 중인 파일의 디렉토리만
:CCGenInfo          " 생성 없이 추론 결과 미리보기 (인자 동일)
```

- `git ls-files`로 스캔한다 (submodule 내부 포함, 비-git 프로젝트는 파일시스템 스캔으로 자동 전환)
- 소스가 10,000개를 넘으면 생성 전에 확인을 받는다 — 대형 트리는 clangd 인덱싱 메모리가
  수십 GB에 달해 시스템 멈춤(스와핑)이나 OOM이 발생할 수 있으므로, 취소하고
  `:CCGen <디렉토리>`로 작업 영역만 좁혀 생성하는 것을 권장 (전체 트리 검색은 gtags 담당)
- 각 소스가 실제 include 하는 경로만 그 파일의 `-I`로 기록 → 대형 트리에서도 파일 크기 안전
- 생성 직후 clangd가 백그라운드 인덱싱을 시작한다 (대형 트리는 수 분, `~/.cache/clangd/`에 캐시)
- 생성물은 절대 경로를 포함하므로 커밋하지 말 것 (프로젝트 gitignore 권장)

크로스 컴파일 등 프로젝트별 설정은 루트에 `.ccgen.lua` 파일로 지정한다 (선택):

```lua
return {
  compiler = "/opt/toolchain/bin/arm-linux-gnueabihf-gcc",
  flags = { "--target=arm-linux-gnueabihf", "--sysroot=/opt/tc/sysroot" },
  extra_includes = { "/opt/tc/sysroot/usr/include" },
  source_dirs = { "src", "lib" },   -- 지정 시 이 경로만 스캔
  ignore_dirs = { "build" },
}
```

### gtags 전체 트리 검색 (Ctrl-\)

GNU Global 패키지가 설치되어 있어야 한다 (`apt install global` — `gtags`, `gtags-cscope` 명령 제공). 자세한 사전 요구는 [index의 설치 항목](index.md) 참조.

gtags 자체는 C/C++ 외에도 Java·PHP 등을 내장 파서로 지원하고, universal-ctags/Pygments
연동(`GTAGSLABEL=pygments`)으로 Python·Go 등까지 확장할 수 있는 도구다. 다만 **현재 구성은
C/C++ 확장자만 인덱싱한다** (`gtags.lua`의 `SRC_EXT` 필터) — 다른 언어의 정밀 분석은 LSP
(pyright, vtsls, rust_analyzer)가 담당하는 구성이므로, gtags 대상을 늘리려면 `SRC_EXT`에
확장자를 추가하면 된다 (내장 파서 외 언어는 참조 검색 정밀도가 떨어지는 점 감안).

먼저 DB를 한 번 빌드한다.

| 키 | 동작 |
|----|------|
| `Ctrl-\ b` | gtags DB 빌드 (`:GtagsBuild` — 실제 소스 파일 목록만 인덱싱, submodule 내부 포함) |

빌드 후에는 nvim 안에서의 변경이 **자동으로 증분 반영**되므로 매번 재빌드할 필요가 없다:

- C/C++ 파일 저장, nvim-tree에서의 파일 생성·삭제·이름변경 시 해당 파일만 DB에 갱신
  (`gtags --single-update`, 비동기 — 편집을 막지 않으며 대형 DB에서도 1초 안팎)
- GTAGS가 있는 프로젝트에서만 동작하고, 없는 곳에서는 아무 일도 하지 않는다
- nvim **밖**에서의 변경(git pull, 브랜치 전환, 셸 파일 조작)과 폴더째 삭제는
  자동 반영되지 않는다 — 이때만 `Ctrl-\ b`로 전체 재빌드

커서를 심볼에 두고 누르면 프롬프트 없이 즉시 검색된다:

| 키 | 동작 |
|----|------|
| `Ctrl-\ g` | 정의 검색 |
| `Ctrl-\ s` | 참조 검색 (심볼을 쓰는 모든 곳) |
| `Ctrl-\ c` | 호출자 검색 (이 함수를 부르는 곳) |
| `Ctrl-\ t` | 텍스트 검색 |
| `Ctrl-\ e` | egrep 패턴 검색 |
| `Ctrl-\ f` | 커서 밑 파일 열기 |
| `Ctrl-\ i` | 이 파일을 include 하는 파일 검색 |
| `Ctrl-\ a` | 이 심볼에 값을 대입하는 곳 검색 |

`d`(이 함수가 호출하는 함수)는 gtags-cscope 미지원 — 함수 본문에서 `Ctrl-]`로 따라간다.

결과가 한 건이면 바로 점프하고, 여러 건이면 Telescope 팝업이 normal 모드로 열린다:

| 키 | 동작 |
|----|------|
| `j` / `k` | 항목 이동 |
| `Enter` | 선택·점프 (팝업 자동 닫힘) |
| `i` 또는 `/` | 필터 입력 시작 |

## 설정 동기화 (저장소 ↔ 실사용)

저장소(`~/MyVim/nvim`)와 실사용 설정(`~/.config/nvim`)을 일치시키는 방법은 두 가지가 있다.
운영 방식에 따라 취사선택한다.

### 방법 1: 수동 복사

저장소와 실사용을 분리해 두고, 변경을 검증한 뒤 rsync 로 반영한다.

```bash
# 저장소 → 실사용 반영 (변경분만 복사, 저장소에서 지운 파일은 실사용에서도 제거)
rsync -av --delete ~/MyVim/nvim/ ~/.config/nvim/
```

- `-v` 출력이 반영된 파일 목록을 보여주므로 별도 확인(diff) 단계를 겸한다
- 장점: 실사용에 올리기 전 저장소 쪽에서 검증할 수 있고, 실사용에서의 임시 실험이
  저장소를 오염시키지 않는다
- 단점: 반영을 잊으면 두 곳이 어긋난다(드리프트) — 어느 쪽이 최신인지 헷갈리기 쉽다.
  `--delete` 는 실사용 쪽에만 있는 파일을 지우므로 로컬 전용 파일을 두지 말 것

### 방법 2: 심링크

실사용 위치가 저장소를 직접 가리키게 해 동기화 자체를 없앤다.

```bash
# 1. 기존 실사용 설정 백업 (저장소와 동일함을 확인했다면 제거해도 됨)
mv ~/.config/nvim ~/.config/nvim.bak

# 2. 저장소를 실사용 위치로 심링크
ln -s ~/MyVim/nvim ~/.config/nvim

# 3. 정상 로드 확인
nvim --headless "+lua print('OK')" "+qa"
```

- 장점: 저장소 수정 = 실사용 즉시 반영, 드리프트 원천 차단. nvim이 갱신하는
  `lazy-lock.json`(플러그인 버전 잠금)도 자동으로 저장소에 잡혀 커밋 대상이 된다
- 단점: 실사용에서의 모든 실험·임시 변경이 곧바로 저장소 working tree에 나타난다 —
  `git status`가 관리 지점이 되므로 커밋 전 확인이 습관이 되어야 한다

되돌리기: `rm ~/.config/nvim && mv ~/.config/nvim.bak ~/.config/nvim`
